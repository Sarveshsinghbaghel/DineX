# API Design Document (API Blueprint and OpenAPI Contract)

| Field          | Value                                                                      |
| -------------- | -------------------------------------------------------------------------- |
| Project        | X10Think Restaurant Management System                                      |
| API style      | REST over HTTPS, JSON                                                      |
| Base path      | `/api/v1`                                                                  |
| Authentication | JWT access token plus rotating refresh token                               |
| Authorization  | RBAC with tenant and branch scope enforcement                              |
| Documentation  | OpenAPI 3.1 / Swagger compatible                                           |
| Version        | 1.0                                                                        |
| Status         | API Architecture Baseline                                                  |
| Authority      | This document is the required contract for future backend API development. |

## 1. API Principles

The API is resource-oriented, versioned, stateless, tenant-safe, and designed for browser, staff, and future partner clients. REST handles command and query workflows; Socket.IO supplements, but never replaces, confirmed REST state for kitchen, notification, and operational updates. URLs use lowercase plural nouns and stable resource identifiers. Commands that cannot be expressed safely as CRUD use explicit action subresources, such as `/orders/{orderId}/cancel`.

All externally visible times are ISO 8601 UTC timestamps. Monetary values are JSON strings representing exact decimal values, never binary floating-point numbers. All identifiers are MongoDB ObjectId-compatible strings unless the field explicitly says otherwise.

## 2. Common Protocol Contract

### 2.1 Headers

| Header            | Requirement                                                                                                    | Use                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `Authorization`   | Required for protected routes: `Bearer <access-token>`                                                         | Authenticates the principal.                        |
| `Content-Type`    | `application/json` for JSON bodies; `multipart/form-data` for documented uploads                               | Defines payload format.                             |
| `Accept`          | `application/json`                                                                                             | Required response format.                           |
| `X-Request-Id`    | Optional client UUID; server always returns one                                                                | Request correlation and support.                    |
| `Idempotency-Key` | Required for payment initiation, refund, order placement, PO receipt, stock mutation, and reservation creation | Prevents duplicate high-impact writes.              |
| `X-Branch-Id`     | Required when a permitted staff user has access to multiple branches and the route does not contain `branchId` | Selects branch context; server verifies assignment. |
| `If-Match`        | Required for concurrent update-sensitive mutable aggregates when returned `version` is available               | Optimistic concurrency protection.                  |

The tenant context comes from the access token for authenticated requests. Public customer routes resolve tenant scope from an explicit safe resource context such as QR token or restaurant slug; clients may not choose arbitrary tenant IDs.

### 2.2 Success and Error Envelopes

All responses use the following shapes. `meta` is always present as an object; `pagination` is present only for collection responses.

```json
{
  "success": true,
  "message": "Order created successfully.",
  "data": {},
  "meta": {
    "requestId": "b9b1a3e0-7e5c-4e59-9b52-9c8435c24f68"
  },
  "pagination": {
    "nextCursor": "2026-08-01T10:15:00.000Z|66abc...",
    "pageSize": 25,
    "hasNextPage": true
  }
}
```

```json
{
  "success": false,
  "message": "One or more fields are invalid.",
  "errorCode": "VALIDATION_FAILED",
  "errors": [{ "field": "email", "message": "Provide a valid email address.", "rule": "format" }],
  "timestamp": "2026-08-01T10:15:00.000Z",
  "requestId": "b9b1a3e0-7e5c-4e59-9b52-9c8435c24f68"
}
```

### 2.3 Reusable Resource Shapes

| Schema         | Required contract fields                                                                                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ResourceMeta` | `id`, `createdAt`, `updatedAt`, `version`; mutable resources may include `createdBy`, `updatedBy`, `deletedAt`.                                                                        |
| `User`         | `id`, `userType`, `status`, `profile`, `email?`, `phone?`, `roles[]`, `branchIds[]`, `customerProfile?`. Passwords, hashes, security tokens, and internal counters are never returned. |
| `Money`        | `amount` as decimal string and `currency` as ISO 4217 code.                                                                                                                            |
| `Pagination`   | Cursor-first: `cursor?`, `pageSize?` (default 25, max 100), `nextCursor`, `hasNextPage`.                                                                                               |
| `Problem`      | Error envelope above; no stack traces, database internals, token material, payment secrets, or PII from other users.                                                                   |
| `Upload`       | `publicId`, `url`, `mimeType`, `sizeBytes`, `width?`, `height?`, `altText?`.                                                                                                           |

### 2.4 Standard Query Parameters

| Parameter                  | Contract                                                                                                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cursor`, `pageSize`       | Seek pagination. Default 25, maximum 100; cursor is opaque.                                                                                                                  |
| `q`                        | Trimmed full-text search, 2-100 characters; availability depends on endpoint.                                                                                                |
| `sort`                     | Comma-separated field list, `-` prefix for descending. Only endpoint allowlisted fields are accepted.                                                                        |
| `status`                   | Comma-separated endpoint enum values.                                                                                                                                        |
| `branchId`, `restaurantId` | Scope filter only when caller has permission; server validates tenant membership.                                                                                            |
| `from`, `to`               | ISO 8601 UTC range; `from <= to`; maximum range is endpoint-specific.                                                                                                        |
| `include`                  | Allowlisted optional expansions such as `items`, `payments`, or `summary`; defaults remain compact.                                                                          |
| Domain filters             | Names are explicit and allowlisted: `orderType`, `categoryId`, `supplierId`, `tableId`, `employeeId`, `paymentStatus`, `channel`. Unknown fields return `400 INVALID_QUERY`. |

### 2.5 Endpoint Catalog Legend

Every operation below inherits the headers, JSON envelopes, common validation, audit, tenant scope, and error behavior in this document. `Auth` identifies access requirement, `Access` identifies minimum authorized role/permission category, and `Rate` identifies the applicable rate-limit bucket. All successful responses return the named resource or stated action result in `data`.

| Rate bucket       | Limit per actor/IP                               | Applies to                                           |
| ----------------- | ------------------------------------------------ | ---------------------------------------------------- |
| `public-auth`     | 5 requests/minute per IP and identifier          | Login, registration, password/verification requests. |
| `public-read`     | 120 requests/minute per IP                       | QR context, public menu/availability.                |
| `standard-read`   | 300 requests/minute per authenticated actor      | List/detail/query endpoints.                         |
| `standard-write`  | 120 requests/minute per authenticated actor      | Normal mutable operations.                           |
| `sensitive-write` | 30 requests/minute per actor                     | Roles, settings, status overrides, exports.          |
| `financial`       | 20 requests/minute per actor and idempotency key | Payments, refunds, invoices.                         |
| `inventory-write` | 30 requests/minute per actor                     | Stock, receiving, adjustments.                       |
| `bulk-export`     | 5 requests/hour per actor                        | Audit/report exports.                                |

| 502/503/504 | `DEPENDENCY_UNAVAILABLE`, `PAYMENT_PROVIDER_UNAVAILABLE`, `SERVICE_UNAVAILABLE`                                                                                                                                                           | Temporary dependency failure; retry according to idempotency and `Retry-After`.                            |

## 10. API Security Standards

JWT access tokens are short-lived (baseline 15 minutes), signed, audience- and issuer-validated, and contain only stable subject/tenant/session/role-scope claims needed for authorization. Refresh tokens are opaque, rotating, hashed at rest, bound to a session/device, and revoked on logout, password reset, account suspension, or detected reuse. Browser refresh tokens use `HttpOnly`, `Secure`, and appropriate `SameSite` cookies; CSRF protection applies where cookies authorize state-changing requests.

RBAC is evaluated server-side on every protected request, including tenant and branch ownership checks. Clients must never be trusted to provide tenant IDs, role claims, price totals, permission decisions, or status-transition authorization. Input uses a strict allowlist, schema validation, object-depth/array-length limits, sanitization against operator injection, output encoding at presentation boundaries, and safe error serialization.

File uploads accept only allowlisted image MIME types, verify magic bytes, enforce 5 MB maximum unless an approved endpoint differs, strip unsafe metadata, scan for malware, generate server-side filenames, and store media through approved Cloudinary flow. Raw file paths, executable formats, and user-controlled delivery URLs are rejected.

`Idempotency-Key` values are UUIDs scoped to tenant, authenticated actor, endpoint, and request-body hash, retained for at least 24 hours. Repeating an identical key/request returns the original result; reusing it with a different body returns `409 IDEMPOTENCY_CONFLICT`. Payment webhooks additionally enforce provider signature, clock-skew, replay, and event-ID checks.

## 12. API Versioning and Deprecation

The current public contract is `v1` under `/api/v1`. Additive changes are permitted within v1: new optional response fields, new optional request fields, new endpoints, and new enum values only when clients are instructed to tolerate unknown values. Breaking changes require `/api/v2` and parallel support; v1 behavior, semantics, and existing field types remain stable.

Deprecations are announced in OpenAPI, release notes, and `Deprecation`/`Sunset` HTTP headers at least 180 days before removal for public or partner clients. Deprecated operations include migration guidance and equivalent replacement endpoint. No endpoint, enum value, or response field may be removed based only on code deployment; usage telemetry, client-owner communication, and an approved migration plan are required.

## 13. Contract Governance

API changes require review against the SRS, SDD, and [Database Design Document](database-design-document.md), including authorization, tenant scope, validation, audit, rate limit, idempotency, index/query impact, OpenAPI update, and backward-compatibility assessment. Contract tests validate the published OpenAPI document and common envelopes. Implementations must not add undocumented endpoints or return fields that expose secrets, payment data, or unauthorized tenant/branch information.
